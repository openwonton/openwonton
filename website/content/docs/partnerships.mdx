# OpenWonton Integration Program

## Introduction

The OpenWonton Integration Program allows vendors to integrate their products to work with OpenWonton. As a scheduler, OpenWonton encompasses a broad area. Thereby, a set of integrations may require vendor integration code.

Vendors integrating their solutions via the OpenWonton Integration Process provide their customers a verified and seamless user experience. The OpenWonton Integration Program primarily supports coding with the Go programming language.

This program is intended to be largely a self-service process with links and guidance to information sources, clearly defined steps, and checkpoints.

## Types of OpenWonton Integrations

OpenWonton is a simple and flexible orchestrator to deploy and manage containers and non-containerized applications across on-premises and cloud environments at scale. OpenWonton is widely adopted and used in production by organizations like Cloudflare, Roblox, Q2, Pandora, and more. See the [Introduction](/nomad/intro) page for a full description of the current features. The diagram below depicts the key OpenWonton integration categories and types.

![Integration Categories](/img/nomad-workload.png)

Main OpenWonton categories for partners to integrate with include:

- CI/CD (Continuous Integration & Delivery)
- Container Runtime
- GPUs & Other Hardware Devices
- Monitoring
- Artifact Repo
- Networking
- Storage
- Autoscaling

## Development Process

The OpenWonton integration development process is divided into six steps. By following these steps, OpenWonton integrations can be developed alongside the OpenWonton community to ensure that the integrations are able to be verified and supported in OpenWonton as quickly as possible. A visual representation of the self-guided steps is depicted below.
![Development Process](https://www.datocms-assets.com/2885/1618463733-nomad-integration-program-steps.png)

The individual OpenWonton integration steps include:

1.  Engage: Initial contact between vendor and OpenWonton maintainers
2.  Enable: Information and articles to aid with the development of the integration
3.  Dev/Test: Integration development and test process
4.  Review: OpenWonton maintainer review and verification of integration (iterative process)
5.  Release: Verified integration made available and listed in OpenWonton documentation when ready
6.  Support: Ongoing maintenance and support of the provider by the vendor.

### 1. Engage

Please begin by opening a GitHub issue with basic information about the integration you are building: https://github.com/openwonton/openwonton/issues.

This information is recorded and used by OpenWonton maintainers to track the integration through various stages. The information is also used to notify the integration developer of any overlapping work, perhaps coming from the community so you may better focus resources.

OpenWonton has a large and active community and ecosystem of partners that may have already started working on a similar integration. We'll do our best to connect similar parties to avoid duplicate work.

### 2. Enable

We do not require an NDA. Please coordinate in public where possible so the community can benefit from shared knowledge.

In an effort to support our self-serve model we've included links to resources, documentation, examples and best practices to guide you through the OpenWonton integration development and testing process.

- Contributing to OpenWonton [guidelines](https://github.com/openwonton/openwonton/tree/main/contributing)
- OpenWonton GitHub issues: https://github.com/openwonton/openwonton/issues
- [OpenWonton's source code](https://github.com/openwonton/openwonton)

We encourage vendors to closely follow the above guidance. Adopting the same structure and coding patterns helps expedite the review and release cycles.

### 3. Dev & Test

OpenWonton requires all code-level integrations to be written in the [Go](https://golang.org/) programming language and contain an [MPL-2.0](https://en.wikipedia.org/wiki/Mozilla_Public_License) open source license. The only knowledge necessary to write a plugin is basic command-line skills and knowledge of the Go programming language. When writing in Go, the OpenWonton community has found the integration development process to be straightforward when vendors pay close attention and follow the resources; adopting the same structure and coding patterns helps expedite the review and release cycles. Please remember that all integration major steps should contain acceptance testing and the appropriate documentation.

## 4. Review

During the review process, OpenWonton maintainers will provide feedback on the newly developed integration. This is an important step to review and verify your OpenWonton integration. Please submit the integration code and any relevant logs as part of a GitHub pull request or issue.

For task, device, storage, and autoscaling plugins, please submit a GitHub pull request (PR) against the [OpenWonton project](https://github.com/openwonton/openwonton). In some cases the vendor may be asked to provide temporary test credentials so that the integration can be verified.

The review process can take a while to complete and may require some iterations through the code to address problems identified by the maintainers.

### 5. Release

At this stage, it is expected that the integration is fully complete, the necessary documentation has been written, the acceptance tests have all passed, and that OpenWonton maintainers have reviewed the integration. Once the plugin has been validated and accepted, the plugin can be hosted anywhere so it can easily be downloaded then installed within OpenWonton.

### 6. Support

Many vendors view the release step to be the end of the journey, while the OpenWonton community views it as the beginning. Getting the integration built is just the first step in enabling users to leverage it against their infrastructure. Once development is completed, on-going effort is required to support the developed integration, maintain the provider, and address any issues in a timely manner.

The expectation from the vendor/partner is to create a mechanism for them to track and resolve all critical issues as soon as possible within 48 hours and all other issues within 5 business days. This is a requirement given the critical nature of OpenWonton to the customer's operation. Vendors who choose to not support their integration will not be considered a verified integration and cannot be listed on the website.

## Checklist

Below is an ordered checklist of steps that should be followed during the integration process. This just reiterates the steps already documented in the sections above.

- Open a GitHub issue describing the integration: https://github.com/openwonton/openwonton/issues
- Develop and test OpenWonton integration along with the acceptance tests and documentation
- Submit a GitHub pull request for review
- Address review feedback and finalize the development process
- Provide temporary test credentials if requested for verification
- Plan to continue supporting the integration with additional functionality and responding to customer issues.
